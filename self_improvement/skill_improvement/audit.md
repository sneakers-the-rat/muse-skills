Previous step results and the run packet carry the whole corpus. Work from them rather than re-deriving it.

- Read the objective run ledger for which loops succeeded, failed, repaired, or kept re-deriving the same suppressed output. The deterministic audit's rollups and candidate findings are your starting hypotheses. Adopt, sharpen, or reject them against the raw evidence. They are not conclusions.
- Read delegated-agent outcomes and scheduled-job results for where delegated work actually failed. A skill that errors under a scheduled worker but not in chat, or an agent that times out on the same step every day, is where failed and learned skills live. Read the failure detail, not just the count.
- Treat repeated tool and work-item failures with the same shape as a missing instruction or a wrong contract somewhere.
- Read delegated-agent transcripts for what delegated agents were actually asked and what they answered. They show the soft failures their terminal outcomes hide.
- Use the run packet's conversation, scheduled-work, and artifacts windows. Built or interrupted work, scheduled job state, and user adjustments after a build are high-value signals for a repeatable build habit, a missing capability, or a repair pattern. The packet also carries prior handoffs and compact objective-step summaries. Use those for objective-step outcomes rather than raw internal logs.
- Read the calibration history for changes already published and what measurement said about them. A prior change that measured `hurt` or stayed `insufficient` past its window is grounds for a retirement-shaped proposal, not another layer on top. A period with no relevant task is inconclusive, so do not retire a sound skill or connector doc only because it went unused.
- Start from the run brief's list of files learned in earlier runs, which names every custom skill and connector doc this loop manages. When it asks for consolidation, do that before you propose anything new.
- Read the skill and connector doc inventories. Each entry carries its revision, its learning metadata and any local amendments. An amendment marked for review has a system base that changed after it was reviewed. Recovered notes awaiting review hold guidance carried over from the previous skill layout. To finish a review, propose the note at its inventory revision with the corrections it needs, or retire it. A note you keep as it is stays marked for review.
