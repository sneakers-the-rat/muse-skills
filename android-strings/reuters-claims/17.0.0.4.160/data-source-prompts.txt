Active notifications surfaced by the system notification listener. Each entry has `app`, `app_package`, `title`, `body`, `sender`, `category` (one of msg, email, social, call, missed_call, other — `call` is a placed or in-progress call, `missed_call` is one the user missed; never treat them as the same thing), and `dedup_key` (a stable id for the same physical message across re-emissions — use it to avoid reporting a notification twice). In messaging notifications, `sender` identifies each message's author, including the user's own replies. `title` labels the notification or conversation, not necessarily the sender. For when it arrived use `timestamp_local` (the user's local wall-clock time), `timestamp_local_date` (their local calendar day), and `timestamp_weekday` (their local weekday name). `timestamp` is UTC and internal — NEVER show it to the user and never use it to compute the day, date, or weekday: it names the wrong day for notifications that arrived in the evening. Show the weekday using `timestamp_weekday` verbatim.

Create a new calendar event. `calendar_id` is optional. Only pass it when a matching calendar ID is available in the current `calendars` array published by the `calendar` data source. Do not guess calendar IDs and do not reuse stale IDs from memory; omit `calendar_id` when unsure, when no calendar preference was requested, or when the current data-source payload does not contain a matching calendar. When `calendar_id` is omitted or stale, Android creates the event in the best visible, syncing writable calendar available. Picking a calendar: (1) if the user names a provider in the canonical list ('Google', 'Outlook', 'Samsung', 'Yahoo', 'Exchange', 'iCloud', 'Fastmail', 'Proton'), filter the `calendars` array by the matching `provider` field. Within those filtered results, prefer calendars with `is_owner_account=true` AND `is_primary=true` (the user's own primary calendar) over shared/group calendars like Google 'Family' or subscribed calendars — only pick a non-owner calendar if the user explicitly names it (e.g. 'Family calendar', 'work shared calendar'). Do NOT fall back on is_primary across providers in this case. (2) if the user names a provider not in the canonical list, do a case-insensitive substring match of the spoken name against `account_type`, `account_name`, and `display_name` and pick from any matches; (3) if the user names an account by email, match on account_name; (4) only if the user gives no signal, pick the calendar with `is_owner_account=true` AND `is_primary=true`, preferring Google > Outlook > Exchange > iCloud > Yahoo > Samsung. On Samsung devices is_primary often points at a Samsung system calendar the user does not actively use, and a Google account auto-creates a 'Family' group calendar — neither should be the default pick when ambiguous. Use this for requests like 'Schedule a meeting at 3pm', 'Add lunch with Sarah to my calendar', 'Block off tomorrow morning'. To create a repeating event (e.g. 'every night at 10pm', 'every weekday standup'), pass an iCalendar `rrule` such as 'FREQ=DAILY' or 'FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR'; a recurring event sets its length with `duration` (ISO-8601, e.g. 'PT1H', default 1 hour) and must NOT also pass `end_time`. Always pass `events_json`, a JSON array string of event objects, even for one event. Each object must include `title` and `start_time`; optional per-event fields are `calendar_id`, `end_time`, `description`, `location`, `all_day`, `timezone`, `reminder_minutes`, `rrule`, and `duration`.

Delete a calendar event. Use this for requests like 'Cancel my 4pm call', 'Remove the meeting tomorrow', 'Delete my dentist appointment'. Get the event_id from the `events` array of the `calendar` data source first. For a recurring event, the data source gives each occurrence a composite id of the form '<id>#<occurrence ISO date>'; passing that id deletes just that one occurrence, while passing the bare numeric id (or `scope`= 'all_events') deletes the whole series. Always pass `targets_json`, a JSON array string of target objects, even for one event. Each object must include `event_id` and may include `scope` ('this_event' or 'all_events'). Always confirm with the user before deleting.

Delete one or more existing device contacts silently after user approval. Use this only when the user explicitly asks to remove saved contacts. Always pass targets_json as a JSON array string, even for one contact. Each target object must include either platform_id from the contacts data source's platformId field or raw_contact_id returned by contacts.create. Do not call contacts.delete once per contact when the user asks to delete multiple contacts; batching keeps this as one user-approved action. This writes directly to the Android Contacts provider; it does not open the Contacts app.

Health Connect data (aggregates, workouts, sleep, events) pushed via observer-driven background sync. Time fields on these rows are epoch SECONDS, not milliseconds — `start_epoch_sec`/`end_epoch_sec`, and `start_ts`/`end_ts` on raw samples, which are the same unit despite the shorter name. Every other Hatch data source sends milliseconds, so do not compare these to another source's timestamps without accounting for the 1000x difference. Rows also carry `timezone`, a UTC OFFSET such as "-07:00" or "Z" (never an IANA region name); use it to place a record in the user's local day rather than reading the epoch value as UTC.

List the reminders (alerts) currently set on one or more calendar events. Use this for 'What reminders are on my dentist appointment?' or before adding/removing an alert. Get the event_id from the `events` array of the `calendar` data source first. Always pass `targets_json`, a JSON array string of target objects, even for one event. Each object must include `event_id`. Returns each event's reminders with their `minutes_before`.

Remove reminders (alerts) from a calendar event. Use this for 'Remove the alert on my meeting' or 'Turn off the 1-day reminder for my trip'. Get the event_id from the `events` array of the `calendar` data source first. Omit `minutes_before` to remove all reminders on the event, or pass it to remove only the matching alert. Always pass `targets_json`, a JSON array string of target objects, even for one event. Each object must include `event_id`; optional `minutes_before`.

Set or update a reminder on a calendar event. By default this replaces any existing reminders on the event; pass `replace`=false to add an extra alert instead. Use this for requests like 'Remind me 30 minutes before my next meeting', 'Set an alert 1 hour before the dentist appointment', 'Also remind me a day before'. Get the event_id from the `events` array of the `calendar` data source first. Always pass `reminders_json`, a JSON array string of reminder objects, even for one reminder. Each object must include `event_id` and `minutes_before`; optional `replace` (default true).

Update an existing calendar event. Only the fields you provide will be changed; omitted fields stay the same. Use this for requests like 'Move my 3pm meeting to 4pm', 'Change the location of my lunch meeting', 'Rename my afternoon event', 'Make my standup repeat every weekday', 'Remind me 15 minutes before'. Get the event_id from the `events` array of the `calendar` data source first. Pass `rrule` (with optional `duration`, ISO-8601, default 'PT1H') to make an event repeat — do not also pass `end_time` in that case. Pass `reminder_minutes` to set the alert lead time (replaces existing reminders), `timezone` to change the event time zone, or `calendar_id` to move the event to another calendar. For a recurring event, passing an occurrence's composite id ('<id>#<occurrence ISO date>') edits just that occurrence (only `title`, `start_time`, `end_time`, `description`, `location`, `all_day` apply); pass the bare numeric id or `scope`='all_events' to change the whole series. Always pass `updates_json`, a JSON array string of update objects, even for one event. Each object must include `event_id` and may include `scope` ('this_event' or 'all_events'); optional per-event fields are `title`, `start_time`, `end_time`, `description`, `location`, `all_day`, `rrule`, `duration`, `reminder_minutes`, `timezone`, and `calendar_id`.

Update one or more existing device contacts silently after user approval. Use this only when the user explicitly asks to change saved contacts. Always pass updates_json as a JSON array string, even for one contact. Each update object must include either platform_id from the contacts data source's platformId field or raw_contact_id returned by contacts.create, plus at least one replacement field such as display_name, phone_number, email, organization, job_title, or note. Do not call contacts.update once per contact when the user asks to update multiple contacts; batching keeps this as one user-approved action. This writes directly to the Android Contacts provider; it does not open the Contacts app.
