Find options for your speaking voice, including browsing for new voices or choosing one for the user.  Use this during a live voice call or from text chat when the user asks for voice options, describes how the voice should sound, or wants a different voice without naming one. It recommends matching voices and, in a live voice call, can switch to the best match when the user asks for a kind of voice, not just to see options.

When the user names exactly one specific voice, picks from options shown on screen, or asks to switch back to a previous voice, use `voice.set` instead.
A self-contained voice request in the user's terms: confirmations and references resolved from the conversation, preferences established there, and the original request when the user answers a clarification question. Describe the wanted voice's qualities rather than a change relative to the current voice, unless the user explicitly asks for one. Never a bare confirmation. Do not add the current voice's name; for a relative request while a custom or saved voice is current, include its qualities from the conversation.
Determine the gender parameter for every voice-options request. Apply the first applicable rule below and
stop. Use F for feminine, M for masculine, and any for neutral or unrestricted gender. Never use N.

1. Explicit request: follow the user's requested gender. Use any when they allow any gender, explicitly
   request a neutral voice, or request a different gender without naming one.

2. Refinement: if no gender was explicitly requested and the user asks to modify a particular current or
   previously offered voice, or adjust a previously offered set of options, use the referenced voice's
   gender. For a set, use F or M only if all referenced options share that gender; use any for mixed-gender
   options or explicitly neutral voices. If the referenced gender is unknown, omit the parameter. Do not
   use persona or name evidence for refinements. Browsing or choosing a new voice is not a refinement,
   even if a current voice exists or the user wants it left unchanged until choosing.

3. Explicit persona evidence: for a new selection, check SOUL.md and IDENTITY.md for statements of your
   gender or gendered pronouns describing you. They/them alone does not establish a neutral/nonbinary
   identity. If the files contain conflicting gender evidence, omit the parameter and stop; do not use
   the name fallback. If there is unambiguous explicit evidence, set that gender. If there is no explicit
   gender evidence, continue to the name fallback.

4. Name fallback: if there is no explicit persona gender evidence, use the assistant's own name recorded
   in IDENTITY.md, not the user's name or names mentioned elsewhere. If it is unambiguously associated
   with a gender, set F or M. For example, Katherine is overwhelmingly female; Hepburn is ambiguous
   despite its association with female actresses. Chris and Jaime are ambiguous first names. Leave
   culturally ambiguous or otherwise uncertain names unresolved and omit the parameter.

Do not omit gender merely because the user did not request it, is only browsing, or wants the saved voice
left unchanged. Do not infer gender from visual traits, professions, personality, other voice traits, or
other indirect evidence. Do not ask the user about gender. Omitting the parameter keeps the current
voice's gender at runtime.
Set an accent only if the user asks you for a specific accent for the voice, using their wording. Keep the accent in the `request` as well. This parameter does not change the language you respond in.
