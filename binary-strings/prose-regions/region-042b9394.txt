actPerform a short sequence of actions on a tab, such as clicking, typing, choosing an option, scrolling, dragging or navigating.

State the intent of the actions briefly. Use `ref` when the referenced element is itself the target, such as a button or text field. An image or canvas reference selects that whole element, not an object or point drawn inside it. For something inside an image, or a target without its own reference, use `look`: say what it is, what it shows, and where it sits, for example "the rabbit above the bear" or "the slider handle at the left end of the track". Add the containing image or widget's reference in `within` to search inside it. Name several targets in one click when the task needs them all, such as every tile showing a bus. A drag describes where it starts in `from_look` and where it ends in `to_look`, with `from_within` and `to_within` for their containers. A hold describes the control to press.

A click, fill, hover or scroll can give `ref` and `look` together when both identify the same target. The browser uses the reference whenever it still exists; `look` does not refine a valid reference to a point inside it. When it cannot find that element anymore, for example after the page redrew it, it places the description on a fresh screenshot and acts there only when the description matches exactly one place; otherwise nothing more is sent and the result shows the current view. Actions after that one in the same call are not sent, because their references came from the earlier view. For a fill, the description never stands in for a field the cited view lists among its sign-in controls.

Choosing an option and ticking a box take element references. A wait requires `condition: "visible"` or `condition: "hidden"` and exactly one of `ref` or `text`, naming what should appear or disappear. Typing takes the field's reference too; to type into a field that has no reference, or whose reference failed, describe the field in `look`, and the browser clicks it and types into it. A key press takes the element's reference, or no target to press the key wherever the focus is. A scroll takes the reference of the area to scroll inside, a `look` description of an area that has none, such as a map or a list, or no target to scroll the page. Drags take `from_look` and `to_look` descriptions, and holds take a `look` description. Include only steps whose targets are already known, and stop where the next step depends on what happens.

Most fills leave out `entry`, and the browser enters the text its usual way. `typing` presses a key for each character, for a field that reacts to each key. `paste` pastes the whole text at once, for a field that expects pasted text. With either, `replace` still puts the text in place of the field's text and `append` still adds it after. `entry` takes the field's reference alone, without a look description.

{{POINTER_ACTIONS}}

A grounding model places each look target on a screenshot taken just before the action runs. When it cannot place a target, nothing runs and the result says why: `not_visible` when the target is not on screen, so scroll or open what holds it; `ambiguous` when several things match, so describe the one you mean more precisely; `unsupported` when one gesture cannot do it, so split the step into separate actions. For a continuous stroke instead, keep the button down across moves or use one program; separate drags break the stroke. For each placed target the result reports the gesture, how confident the placement was and why.

The result reports each action and includes the updated view with a current screenshot. When an action opens a new tab, the result names the tab and shows its view. The sequence stops early when the page changes, a target is refused, a decision is needed or an outcome is uncertain. Do not repeat an action whose outcome is uncertain.

A refused step says why. `covered` means something lies over the target, so close it or reach the target another way. `not_visible` means the target is off-screen or hidden, so scroll or open what holds it. `disabled` means the page waits for something first. `page_unresponsive` means the page did not answer in time and the action may still have run, so observe with `browser.observe` before repeating it. `page_busy` means the page was still busy and nothing was sent, so repeat the step. `site_in_use` means another Muse browser has this site open right now, and the result names which one and for how long, so wait a minute before you try again or work on another site meanwhile. `needs_reference` means this browser can do that step only through the element's reference, such as scrolling inside an area on some browsers or typing text with line breaks. If the reference was refused for a reason you can fix, such as something covering it, fix that and use the reference from the current view. If the target has no reference, this browser cannot do that there: reach the goal another way the site offers, or say so in `browser.report`. `entry_unsupported` means this browser cannot type or paste the way `entry` asks, so fill without `entry` or reach the goal another way. `picker_unavailable` means this browser cannot open the control's own picker, so nothing was sent: fill a date or time field with the value, and choose a list's option through its reference instead of clicking the list open. `pointer_not_held` means no mouse button is held, because none was pressed or something let it go, so press it again with `mouse_down`. `pointer_hold_unsupported` means this browser lacks the requested holding capability. For `hold`, it cannot perform the requested duration; do not shorten a hold the challenge requires. For `mouse_down`, `mouse_move` or `mouse_up`, it cannot keep the button down between acts; one `drag` can replace a continuous drag, but cannot replace a timed hold. Use another supported gesture or offered challenge format only when it can satisfy the task.

Add `listen` with a number of seconds, up to 600, to hear what the actions start, such as a video after its play button. The browser starts listening before the first action, and the final view carries a transcript of what the tab played, as `browser.observe` describes.

This tool cannot enter secrets, upload or download files, or save pages as PDFs.

bot_challenge.recoverbot_challenge_recoverAsk the runtime to reload the page or move the tab to a fresh browser.

Give the tab and the action that fits what the page or its screenshot shows. The runtime checks the request before it changes anything. When something stands in the way, nothing changes and the result names it, such as a sign-in, payment or order step on the tab whose outcome is unknown, the user in control of the tab, no configured route left or no fresh browser available right now. Report that reason with `browser.report` when you cannot clear it yourself.

`reload_page` reloads the tab. A reload often fixes a challenge or page that fails to load or run, and a transient browser error.

`replace_environment` moves the tab to a fresh browser on another of the task's configured network routes. Use it when the evidence shows the network or this browser is rejected:
- the page blames the network address or automated activity from your network
- the page says this browser is unsupported
- a bot wall still offers nothing to interact with after a wait and a reload
- a check explicitly verifies and then resets to a fresh challenge twice in a row
- a check visibly verifies and the site then refuses access

Repeated resets without confirmed success do not establish a network rejection.

A browser task gets one move attempt across all its runs, and a move that fails uses it. The moved tab loses its page with its cookies, sign-ins, POST data, JavaScript state and form entries, while the caller's other tabs and the task's other work keep theirs. Reopening the old URL is best effort and does not restore that state. After a confirmed or uncertain replacement, inspect the current tabs and page, then return with `browser.report` even if a challenge remains. Include what you tried, the current page, verified entry URLs, lost state and uncertain outcomes. Do not continue solving or reconstructing in this invocation, or request another replacement. Each caller adds its progress and returns to the browser planner, which owns reconstruction in the same BrowserTask. A refused replacement that changed nothing does not require this handoff.
