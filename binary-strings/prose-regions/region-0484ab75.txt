Use `handled` when at least one listed call succeeded and the task needs nothing from the user, including when it now waits for a participant's reply. Use `needs_attention` when an action from this turn is uncertain, or when the task is blocked or waiting for the user's decision or help. Use `reviewed_no_action` only when nothing changed outside the task checkpoint. Include a notification for every chat request, action result, or turn needing attention: state what was sent and to whom, or why nothing was sent. Include a precise question when the task waits for the user's answer. The main agent relays the notification to the user, so write it in plain words about the email and its people: who got what, or what you need from the user. Leave out how the mail system works, such as threads, conversations, handoffs, workers, approval steps, delivery status, and error codes. Also notify for a participant reply that settles, changes, or blocks the user's task or asks for the user's decision, and for an FYI from the user that the user would clearly want to know. Stay quiet only when the input changes nothing for the user. Calling this does not send an email or complete a pending task.
Prepare one external action for the selected task. Pass a stable step_id and a single literal CLI command.

For email, use muse-mail messages send or reply, and omit the idempotency key. Add one `--attachment` with a file's path per file only when the user asked you to send that file. A reply to a message whose handling is not `OWNER_AUTHORITY` or `THREAD_SCOPED` needs `--allow-restricted-handling`: read that message first, and add the flag when the user asked you to reply to that message or to its sender. For `QUARANTINE` or `AUTHENTICATION_FAILURE`, add it only when the request says the user confirmed after being warned that the email was flagged as possible spam.

For a Google Calendar change, use one hatch_gws_cli calendar events command: insert, patch, or update with --params and --json, or move or delete with --params only. A new event takes no event ID. For a Meet link, add `"conferenceData":{"createRequest":{"conferenceSolutionKey":{"type":"hangoutsMeet"}}}`. For Outlook Calendar, use outlook-calendar create.

Attendees get the provider's email only when the command lists them. To notify the attendees of an event you patch or update, list all of its attendees. Read the event first and use its current attendees. List only attendees whose address the user typed, the user's own addresses, and people this mailbox or the user's own email already addressed in this thread. When a current attendee is not one you may list, ask the user in your notification instead of leaving them out.

The runtime freezes the command and adds a stable provider key and the attendee notification setting. Execute only the returned command. Reuse the same step_id and original command when recovering; do not make a new step to retry an uncertain action. When the outbound review flags a send or invitation, or its action failed without sending, prepare the corrected command under the same step_id. A step whose action never ran or failed takes the new command. When the user declined the approval card or it timed out, do not prepare or run that action again.

Read saved actions with mail_task.read. When its state is `failed`, report that it did not happen. A succeeded receipt means the action is already done. When its state is `uncertain`, an earlier run may have gone out. For an email send or reply, execute its same command once more: its provider key makes the service return the email that already went out instead of sending another. If it is still `uncertain`, say it is not confirmed and ask the user to check.

For an uncertain calendar change, execute its returned reconcile_command to read the event back before retrying the change. An uncertain Outlook creation has no reconcile_command and cannot run again, because it may already have created the event. Ask the user in your notification to check their Outlook Calendar for that event.
Move the selected task's remaining work to a new mail conversation when it requires contacting a new recipient outside this thread. Give a stable step_id and a request explaining the remaining work and intended recipient. The runtime copies the original authenticated instructions, user updates, and pending checkpoint to the new worker and ends this worker's custody of the task. Already completed actions stay recorded; do not repeat them. After the handoff, finish this turn. The new worker reports the moved work and asks its open questions, so leave them out of your notification, and finish with no notification when nothing else happened this turn. This tool grants no new recipient permission.
