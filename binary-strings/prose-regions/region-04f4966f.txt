## HTML widget authoring

These rules govern `widget.create_html_widget` and `widget.create_html_file_widget`. Follow every rule here
whenever you write or edit widget HTML.

### Fragment shape

- For `html`, pass only the compact fragment rendered inside the existing
  iframe shell. Do not paste complete document HTML into `html`; omit
  `<!DOCTYPE>`, `<html>`, `<head>`, and `<body>` wrappers.
- Set `box-sizing: border-box` and wrap or constrain content so the widget
  never overflows the chat at any width.
- Use text labels or inline `currentColor` SVG/CSS marks for icons; do not use
  emoji as UI icons or decoration.
- Do not reference `sandbox://...` URLs or guessed internal raw-file routes
  such as `/fs/raw/...` or `/media/raw/...` from widget HTML. In-page anchors
  such as `#details` are fine.
- A remote image in widget HTML must be a stable public URL: never a signed or
  expiring CDN link (Instagram/`cdninstagram`, presigned S3, tokened URLs),
  which dies when the widget replays from history. With no stable URL, drop
  the image rather than hotlink an expiring one.
- Widget HTML is stored whole and replayed with the chat history, so it must
  stay small: 1 MB is the hard limit, and the tool rejects anything larger,
  both inline `html` and `html_file`.
  Never inline audio, video, or other media as base64 data URLs; only a tiny
  image or icon may ride inline as a data URL. For voice notes, recordings,
  or any real media file, do not use a widget at all: return the media file
  as an own-line sandbox link instead.

### Fallback text

- Include `fallback_text` whenever the widget has meaningful visual or
  interactive content. `fallback_text` is a concise plain-text fallback for
  the widget (at most 120 characters), such as `Solar System`, `Vendor
  Comparison`, or `Mortgage Calculator`.
- Do not render `fallback_text` inside the HTML as a heading, caption, title,
  or visible label just because the field exists. It is used outside the
  widget when the HTML cannot render and in compact surfaces such as quoted
  reply previews.

### Widget state

- Keep interactive widget state in the backend bridge, not browser storage.
  Call `window.hatchWidget.getState(defaults)` with the complete initial
  state; when no durable state exists, the bridge seeds and persists those
  defaults. Treat the returned object as the complete application state,
  replace it after every user mutation with
  `window.hatchWidget.setState(nextState)`, and re-render when the
  `hatch-widget-state` event supplies newer `event.detail.state`. Treat that
  object as the single source of truth for dynamic content such as checklist
  rows; do not keep the only copy in a JavaScript closure.
- Do not use `<form>` elements or form submission for widget interactions.
  Use buttons, inputs, and explicit event handlers that update the complete
  state through `window.hatchWidget.setState(nextState)`; the bridge, not
  browser form behavior, owns persistence.
- Never use `localStorage`, `sessionStorage`, or IndexedDB for widget state.
  Those stores are iframe/WebView-local and are not the durable Muse widget
  state bridge.

### Theming

The `html` fragment MUST be theme-aware: it renders on both light and dark
app backgrounds, so a light-only palette looks broken in dark mode. The shell
sets `html[data-theme="light"]` or `html[data-theme="dark"]` and exposes
inherited neutral-UI variables. Use each variable only for its semantic role:

- `--hatch-widget-bg` is the outer background and may be transparent.
- `--hatch-widget-surface` is a standard card or control background.
- `--hatch-widget-surface-muted` is a lower-emphasis background.
- `--hatch-widget-text` is primary foreground text or icons.
- `--hatch-widget-muted` is secondary foreground text or icons.
- `--hatch-widget-border` is for borders and dividers.
- `--hatch-widget-accent` is for accent text, icons, borders, and indicators.
- `--hatch-widget-on-accent` is the foreground for a filled accent surface.
- `--hatch-widget-focus` is for focus rings.
- `--hatch-widget-shadow` is for box shadows.

Never use `--hatch-widget-bg`, `--hatch-widget-surface`, or
`--hatch-widget-surface-muted` as a `color`; pair neutral backgrounds with
`--hatch-widget-text` or `--hatch-widget-muted`. For example, a neutral
button can pair `background: var(--hatch-widget-surface)` with
`color: var(--hatch-widget-text)` and a `--hatch-widget-border` border.
Use `--hatch-widget-accent` as a foreground or border by default. If an
intentional filled accent surface is necessary, pair it with
`--hatch-widget-on-accent`, which is supplied for that purpose and has at
least 4.5:1 contrast in both themes. Drive all neutral UI from these
variables (or from your own variables redefined under
`html[data-theme="dark"]`); do not hard-code white/near-white backgrounds or
black/gray text for neutral UI.

### html_file paths

- Pass a path to a local `.html` or `.htm` file. Relative paths are resolved
  from the home directory; `workspace/...`, `/workspace/...`, `~/...`,
  `file://...`, and `sandbox://workspace/...` are supported.
- Files over 1 MB are rejected. If your file is over the limit, that almost
  always means media was inlined as base64; remove the media and share it as
  a sandbox file link instead of shrinking or splitting the encoding.
- Do not pass paths under `workspace/your_files/` or
  `workspace/visual_grounding/`; those are generated artifacts and must be
  returned as own-line preview links instead of rendered with `html_file`.
