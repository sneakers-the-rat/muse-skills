## Classification

Answer every section of the schema. A task can have several separate problems. For each problem (a page or action that failed), go down this list and use the first item that fits. Do not put the same problem in more than one of these failure categories. The exception is `challenge_loop`, described under `hard_bot_block`, which is also recorded in `captcha` as `failed`, or as a user outcome when the user then took control of the challenge.

1. `infra_failure`: one of the browser or network failures listed under `infra_failure` stopped it, even when the site caused it (for example, the site's own certificate is invalid). A connection reset, `ERR_HTTP2_PROTOCOL_ERROR`, empty response, or navigation timeout on only one site, while other sites load, is not an infra failure.
2. `hard_bot_block`: the site refused service with no interactive way through.
3. `captcha`: the site presented an interactive human-verification challenge.
4. No failure category: the site gave a reason for the failure (for example, out of stock or a wrong password), the agent made a mistake, or the task was waiting on the user.
5. `soft_block`: nothing above explains the failure, and the step never succeeded later in the task, on this site or another site.

Also fill in `site_workarounds` by its own rules: list each site that stopped the agent and what it tried instead. These entries can accompany a failure category above, or stand alone when the agent recovered on another site.

Then fill in `blocked_sites`: the site where each `hard_bot_block`, `captcha`, or `soft_block` you recorded happened.

Evidence rules:

- Record something only when the evidence shows it: page text, tool output, a tool error, a screenshot, the terminal reason, or the runtime page-load statuses as `hard_bot_block` describes. The browser planner's own words ("I appear to be blocked") can back up that evidence but are never enough on their own. A specialist's report counts as evidence of what it observed: when the runtime hands the agent a `## Specialist sN finished` message, each finding marked `basis: observed` counts as tool output. A specialist's reported status (such as `completed` or `blocked`) is its own claim, not evidence. A specialist the agent started acts for the agent. `purchase_outcome` and `goal_reached_judgment` keep their own evidence rules.
- If the evidence for something is missing, unreadable, or cut off, answer as if it did not happen. `purchase_outcome` and `goal_reached_judgment` have their own rules for unclear evidence. Part of the middle of the history may be cut out; do not guess what it said.
- If nothing happened for a section, answer `[]` for a list, `{"cues": [], "steps": []}` for `hard_bot_block` and `soft_block`, `"none"` for `captcha`, or `false` for `authenticated_session_observed`.
- `goal_reached_judgment` always has exactly one value, including `unknown` when its evidence rules require it. It is independent of which diagnostic sections are populated.

## Steps

`hard_bot_block.steps`, `soft_block.steps`, and `gated_steps_attempted` use these step names. Each step covers loading that step's page and submitting its action:

- `sign_in`: authenticating to an existing account: submitting credentials, restoring a saved login, or submitting a verification code.
- `add_to_cart`: adding an item to a cart, bag, or basket.
- `checkout`: opening the cart, checkout, or payment page, including a booking's traveler-details or passenger-information page.
- `place_order`: submitting the payment or order ("Place order", "Pay", "Book", "Submit").
- `page_load`: any other navigation or page load.

Attribute an incident to the step the agent was trying to perform, not to the page that appeared: a redirect to a sign-in page while checking out is `checkout`. If the incident happens on the first page the task loaded on that site, or every page of the site fails, use `page_load` even on a sign-in, cart, or checkout URL.

List a step in `gated_steps_attempted` when the agent actually did it, whether or not it worked: `sign_in` when it submitted credentials, restored a saved login, or submitted a code; `add_to_cart` when it clicked add to cart; `checkout` when it deliberately opened the cart or checkout; `place_order` when it clicked pay or place order. Do not list `page_load` here. Planning a step, mentioning it, or seeing a link to it does not count.
## infra_failure

List each kind of browser or network failure below that stopped the task or a step it needed. Do not list a failure the agent got past by retrying.

- `tls_certificate`: navigation was blocked by `ERR_CERT_*`, `ERR_SSL_*`, "Your connection is not private", or another certificate or secure-connection error, on any site.
- `network`: `ERR_INTERNET_DISCONNECTED`, `ERR_PROXY_*`, or `ERR_TUNNEL_CONNECTION_FAILED` on any site, or DNS, connection-refused, or timed-out errors on two or more different sites.
- `browser_start_failed`: the browser could not be acquired or launched, so browsing never started or could not resume.
- `browser_session_lost`: the browser crashed, disconnected, closed the tab or target, or stopped responding, and the task could not continue in that session.
- `browser_timeout`: a browser tool command other than navigation (observe, screenshot, click, type) timed out.

DNS/name-resolution failures include `ERR_NAME_NOT_RESOLVED`, `DNS_PROBE_STARTED`, `DNS_PROBE_FINISHED_NXDOMAIN`, and messages such as "DNS address could not be found" or "server IP address could not be found". They count as `network` only when observed on two or more different sites. A lookup failure on one site is not recorded as a failure or site workaround; its attempted page load still counts. Classify any separate failure in the task by its own evidence.

A connection reset, `ERR_HTTP2_PROTOCOL_ERROR`, empty response, or navigation timeout on one site while other sites load is not an infra failure; see `soft_block`.

If nothing qualifies, answer `[]`.
## hard_bot_block

The site, its CDN, or its bot-protection vendor refused to serve a page or action, and offered no interactive way through. Record every occurrence, even if a later retry or a `refresh_environment` action got past it. List each step where it happened in `steps` and every cue you observed in `cues`:

- `vendor_block_page`: a bot-vendor block page: Akamai "Access Denied" with a "Reference #", Cloudflare "Sorry, you have been blocked" or error 1020 with a Ray ID, an Imperva or Incapsula incident ID, or a DataDome or PerimeterX block page.
- `access_denied_page`: any HTTP 403, "Access Denied", or "Forbidden" page, including a bare one with no vendor branding.
- `rate_limit_page`: any HTTP 429, "Too many requests", or "rate limited" page.
- `ip_or_automation_attribution`: the page blames the IP address, network, VPN or proxy, "unusual traffic", or automated or bot activity.
- `auto_check_never_cleared`: an automatic check such as "Just a moment…" or "Checking your browser" was still showing after a wait or reload.
- `challenge_loop`: after the site accepted the agent's CAPTCHA solve (a checkmark appeared or the page advanced), either a new challenge appeared at least twice or the protected page never loaded. When you record this cue, also set `captcha` to `failed`, unless the user then took control of the challenge and `user_solved` or `user_failed` applies. This is the only problem assigned to two failure categories.
- `repeated_access_error`: the site's core action (a search, a booking, adding to cart) failed with the same error page or error code on every attempt, across retries and changed inputs, while other pages on the site loaded. For example, every flight search returned "We're sorry, but there was a problem processing your request. #SFAF001". A single failure, an error that changed or cleared on retry, or an error that states a specific reason such as incorrect credentials, out of stock, unavailable dates, a quantity limit, an invalid address, or a payment decline that gives a reason is not this cue. Apply the other hard-block cues independently; HTTP 403 and 429 remain hard blocks.

Every cue needs page text, a screenshot, or an observed finding in a specialist's report that shows it; `access_denied_page` and `rate_limit_page` can also rest on the runtime page-load record, as described below. Never infer a cue from the browser planner's own narration alone.

A page served as HTTP 403 or 429 is always a hard block, even when it gives a reason such as an account lock or a geographic restriction. A status in the runtime's page-load record counts as page evidence of that status when the history shows the agent needed a page on that site and that page did not work for the agent at least once (an error or block page, an empty or missing result, a retry, or leaving the site), even if a later retry got through: 403 is `access_denied_page`, 429 is `rate_limit_page`, and 999 is `access_denied_page`. If the agent's pages on that site visibly worked and it got what it needed there, the status alone is not a hard block. Treat a recorded 503 or 530 like the server errors below. These are not hard blocks: an interactive CAPTCHA the agent could act on (see `captcha`); a server error (500, 502, 503) or "Failed to fetch" that cleared on retry or that the agent got around on the same site; an HTTP 401; and any other account lock, geographic or licensing restriction, paywall, sign-in wall, request-access prompt, outage, or maintenance page.

A server error (500, 502, 503) or "Failed to fetch" that never cleared is a hard block only when it meets one of the cues above, such as `repeated_access_error`. Otherwise, apply the `soft_block` rules; an explicit outage or maintenance explanation still rules out a soft block.

If nothing qualifies, answer `{"cues": [], "steps": []}`.
## captcha

Record whether an interactive human-verification challenge appeared and how it was finally resolved, by the agent or by the user. Challenges include a reCAPTCHA, hCaptcha, or Cloudflare Turnstile checkbox or image grid, an Arkose or FunCaptcha puzzle, a press-and-hold button, a slider, and a text or audio CAPTCHA. These are not challenges: a check that clears with no agent action, a one-time code sent by email or SMS, an MFA prompt, an age gate, and a cookie banner.

A challenge counts only when page text, a screenshot, or an observed finding in a specialist's report shows the challenge itself: its widget or frame, or instructions such as "I'm not a robot", "Select all images with", "Press and hold", or "Verify you are human". A product, page, or link whose name contains a word like "challenge" is not a challenge, and the agent's narration alone is not evidence. Without that evidence, choose `none`.

Choose exactly one value, checking in this order. The value records how the task's challenges were finally resolved, so a user outcome comes before the agent's: if the agent failed a challenge and the user then cleared it, choose `user_solved`. The user values exist only when the schema lists them; use the runtime user-control record to place the user's control in the history. The agent's narration alone is not evidence that the user acted or controlled the browser.

- `user_solved`: a challenge was cleared while the user controlled the browser, or the first page the agent observed after the user gave control back shows it cleared (its widget is gone and the protected page or next step loaded), and the agent did not interact with that challenge between the user taking control and the challenge clearing.
- `user_failed`: a challenge was showing when the user took control, and it was still showing or still blocking the step when the user gave control back, or when the task ended while the user still controlled the browser.
- `failed`: the agent attempted at least one challenge that was never cleared, and the user did not take control while it was showing: the solve was rejected, the challenge returned without progress, it stayed unreadable after an attempt, the agent's solving tool refused the attempt, or the agent gave up after trying. A `challenge_loop` (see `hard_bot_block`) is also `failed`, even though a solve was accepted.
- `solved`: the agent itself interacted with a challenge (a click, drag or hold on it), and the protected page or next step loaded afterward.
- `not_attempted`: a challenge appeared but nobody tried to solve it: the agent never interacted with it and the user never controlled the browser while it was showing.
- `none`: no interactive challenge appeared.
## soft_block

A soft block is a step that failed when nothing in the evidence explains why. It is the last section to consider: a problem already recorded under `infra_failure`, `hard_bot_block`, or `captcha` is never a soft block. Record a step only when all of these hold:

1. The agent attempted the step: for `page_load`, it navigated to the page; for any other step, it submitted the step's action (see Steps).
2. The site failed with at least one cue:
   - `generic_error_message`: an error that names no cause, such as "Something went wrong", "Unable to sign in right now", "We couldn't process your request", "Error adding to cart", a bare HTTP 500, 502, or 503, or "Failed to fetch".
   - `silent_no_op_after_retry`: the action did nothing visible (no navigation, cart count unchanged), and doing it again also did nothing.
   - `blank_or_spinning_after_retry`: the step's page stayed blank, spinning, or incomplete after a wait or reload, while other pages on the same site loaded.
   - `single_site_connection_error`: `ERR_HTTP2_PROTOCOL_ERROR`, a connection reset or close, an empty response, or a navigation timeout on this site while other sites loaded.
3. Nothing explains it: no site-stated reason, no agent mistake (wrong control, missing required field, validation message), and the task was not waiting on the user.
4. The step never succeeded later in the task, on this site or another site.

An error that meets `repeated_access_error` (see `hard_bot_block`) is a hard block, not a soft block.

A DNS/name-resolution failure is not a `generic_error_message` or `single_site_connection_error`; apply the DNS rule under `infra_failure`.

A site-stated reason rules out a soft block. A sign-in error is explained if it mentions the email, username, password, code, or credentials ("incorrect", "doesn't match", "invalid"), if the user later supplied different credentials, or if the same credentials later worked. Also explained: account locked, verification required, out of stock, quantity limit, invalid address, card declined with a reason, maintenance, and geographic restriction.

If nothing qualifies, answer `{"cues": [], "steps": []}`.
## site_workarounds

Record each site that stopped the agent and what it tried instead. A site stopped the agent when the agent could not get past a step it needed there: the site refused service (see `hard_bot_block`), showed a `soft_block` cue, or the step kept failing or would not proceed. The failure must not be explained by an agent mistake (wrong control, missing required field, or validation message). Count the site even when the agent then succeeded on another site; that recovery is exactly what this section measures.

A site did not stop the agent if it asked for information or a choice the agent did not have (sign-in, traveler details, payment), if it gave a reason such as sold out or unavailable on a page you did not record as a `hard_bot_block`, or if the agent simply preferred another site.

A DNS/name-resolution failure alone does not qualify a site for this section.

Include each site behind a `hard_bot_block` or `soft_block` you recorded, and each site the agent left for another site because it could not get past a step that qualifies under the rules above. Leave out a failure the agent later got past on that same site, for example after `refresh_environment` or a retry. For each remaining site, add one entry for each other site where the agent then tried to get the same thing (the same item, booking, or information), in the order it tried them. If the agent tried no other site, add one entry with an empty `alternate_site` and `not_attempted`.

- `blocked_site` and `alternate_site`: the host from a URL in the evidence, such as `amctheatres.com` or `www.fandango.com`, never a brand name. Use `""` when there is no alternate.
- `outcome`, exactly one value:
  - `unblocked`: on the alternate site the agent got past the step where the blocked site stopped it (for example, it reached showtimes, a booking form, or a cart), even if the task failed later for another reason.
  - `still_blocked`: the alternate site also blocked the agent, or the agent did not get past that step there.
  - `not_attempted`: the agent tried no other site for this goal.

A search engine, or a site the agent only read to compare prices or find links, is not an alternate. If no site qualifies, answer `[]`.
## blocked_sites

The block answers above say what happened; this answer says where. Block rates are broken down by site, and without a site a block gets charged to whichever site the agent used most, which is often the site it moved to after being refused somewhere else.

Add one entry for each site where something you recorded under `hard_bot_block`, `captcha` (any value other than `none`), or `soft_block` happened. `site` is the host from the URL of the page the block appeared on, such as `amazon.com` or `www.walmart.ca`, never a brand name; the tab's URL or the navigation just before the block usually shows it. `kind` is `hard_bot_block`, `captcha`, or `soft_block`, and a site where several kinds happened gets one entry for each. Answer `[]` when you recorded none of the three.
## authenticated_session_observed

Answer `true` when the evidence shows the agent was signed in to at least one site during this task, whether it was already signed in when the task started or signed in during the task. The site itself must show it, for example with content only that account can see or an account page that clearly shows the user is signed in. Answer `true` even if the session later expired or logged out, or the task failed. These are not enough on their own: a login page, an account URL, saved credentials being available, the agent filling in or submitting credentials, an approval to use credentials, or a claim that sign-in worked that nothing on the site confirms.
## goal_reached_judgment

Record the outcome of the requested browser goal for the assessed run.
Read the recorded governing instructions in goal_reached_judgment_scope to determine
the goal and its constraints. Only current_run inputs define this run's
requested results. Read them in recorded order and apply later steering to
the earlier request. prior_run_context inputs can resolve references or
constraints expressly carried forward by current_run instructions; they do
not add prior goals or conditions superseded by current-run input.
Explicit conditions, including a requirement to
obtain approval before acting, remain part of that goal. Independently match
that goal and its material constraints to observed current-run page data,
action results, and screenshots.

Browser hand-off events, browser.report reports, runtime completion_result
values and their completed or failed lifecycle labels, plus agent narration,
summaries, or assurances never establish success. An outcome_eligible marker
only identifies the run; it does not turn such a claim into page or action
evidence. These labels also cannot override an independently verified goal
result.

Use the runtime's evidence annotations. Only history records with
outcome_eligible=true and screenshots listed in eligible_screenshot_indices
can establish this run's result. Screenshot indices start at 1, oldest first.
Ledger entries retain their original context_seq and may describe earlier
work; outcome_eligible=false entries cannot establish the current result.
An outcome_observation_retained=false ledger entry records a call but does not
supply its omitted output as goal evidence. Older receipts, summaries, and
agent claims can resolve references but cannot prove a later request succeeded.
If the run scope or recorded governing inputs are unavailable, choose unknown.
Success, needs_user, and failed require retained current-run browser observations.
For cancelled only, an explicit withdrawal in the recorded current_run governing
inputs can establish the outcome even when no browser observation is retained.
Runtime stop, close, cancelled, or superseded labels alone do not establish that
the requested goal was withdrawn. Closing a browser after a result or while
retaining a user prerequisite can be session cleanup.

Choose exactly one value, checking in this order:

- success: Current page data, action output, a screenshot, or a merchant
  confirmation establishes every requested result and material condition:
  the requested item, variant, quantity, date, target, amount, or final state.
  An accurate negative answer completes a factual lookup. Reaching a requested
  cart or review state can complete a task that expressly stops there. Apply
  requested conditional and fallback branches exactly. For a purchase or
  booking, approval and a successful payment step do not establish final
  placement; require merchant-side confirmation of the requested action. A
  verified requested result remains success after routine browser cleanup.
- cancelled: Recorded current_run governing input explicitly withdraws or
  supersedes the requested goal and ends that work, before a verified requested
  result. A later instruction that changes the goal and continues work in this
  run is steering: judge the resulting goal instead. An earlier-run withdrawal,
  a browser close, an assistant's cancellation claim, or a lifecycle label alone
  cannot establish current-run cancellation.
- needs_user: The result is incomplete and a concrete user-only prerequisite
  remains for a goal still requested: a login wall, verification code, missing
  required information, approval, or a decision only the user can supply. A page
  or tool result must establish the prerequisite; an unsupported request for
  help is not enough.
- failed: The retained observations establish an unmet result from incorrect
  or incomplete execution: the wrong target or date, an omitted required step,
  premature termination with a viable path remaining, or an unrecovered browser
  infrastructure failure. Also use failed when an observed external or policy
  barrier prevents the requested result within its permitted scope, with no
  concrete user-only action that would clear it: persistent access denial, a
  site outage, unavailable inventory for a requested purchase, or a prohibited
  action. Partial progress is not the full requested result.
- unknown: The retained evidence cannot establish the result, including a
  decisive output missing after truncation or unsettled history, conflicting
  results, or only a final completion claim. Missing evidence of success is
  not evidence of failure. A stop or superseded lifecycle state without a
  captured governing withdrawal is unknown when observations cannot establish
  another outcome.

An encountered problem that was later worked around does not override a
verified result. A tool's success boolean alone does not establish the user's
requested result.
## purchase_outcome

The browser task invoked its checkout workflow (`browser.pay`). Set `purchase_outcome` to the merchant result. A cart review that stopped before purchase is `not_submitted`.

Select exactly one `purchase_outcome`. Answer any other sections of the schema by their own rules; the purchase outcome does not change them.

- `succeeded`: The merchant's receipt, order confirmation, or order history verifies that the order was placed.
- `failed`: The merchant definitively rejected the submitted payment or order, and no later evidence verifies that the order was placed.
- `not_submitted`: The browser task did not submit the payment or order to the merchant. Use this when preparation, approval, credential preparation, or wallet application stopped before merchant submission.
- `unknown`: The evidence does not establish whether the merchant placed the order. Use this whether or not the evidence establishes merchant submission.

When `purchase_outcome` is `succeeded`, set `purchase_outcome_reason` to null.

When `purchase_outcome` is `failed`, set `purchase_outcome_reason` to one of:

- `payment_rejected`: The merchant or its payment processor explicitly declined the payment submitted at the merchant's checkout.
- `order_rejected`: The merchant explicitly rejected the submitted order. The evidence attributes the rejection to a cause other than payment.
- `other_rejection`: The merchant explicitly rejected the submitted payment or order, but the evidence does not support a more specific rejection reason.

For `failed`, select the first supported reason in this order: `payment_rejected`, `order_rejected`, `other_rejection`.

When `purchase_outcome` is `not_submitted`, set `purchase_outcome_reason` to one of:

- `approval_denied`: The user explicitly denied the required purchase approval before merchant submission.
- `payment_setup_failed`: Payment approval, credential preparation, or wallet application failed before merchant submission.
- `pre_submission_user_action_required`: The browser task stopped before merchant submission because the user needed to provide information or make a decision. No explicit purchase-approval denial was recorded.
- `other`: The evidence verifies that merchant submission did not happen, but it does not support another `not_submitted` reason.

For `not_submitted`, select the first supported reason in this order: `approval_denied`, `payment_setup_failed`, `pre_submission_user_action_required`, `other`.

Do not use `pre_submission_user_action_required` for user action requested after merchant submission. Classify that case from later merchant evidence, or as `unknown` when no result was observed.

When `purchase_outcome` is `unknown`, set `purchase_outcome_reason` to one of:

- `result_not_observed`: The evidence establishes submission, but no merchant acceptance or rejection was observed.
- `submission_uncertain`: The evidence does not establish whether the purchase submission completed.
- `inconclusive_evidence`: The evidence is contradictory or does not support another `unknown` reason.

For `unknown`, select the first supported reason in this order: `result_not_observed`, `submission_uncertain`, `inconclusive_evidence`.

Use the browser task status, terminal reason, list of the agent's tool calls, agent's message history, and screenshots as evidence. The browser task's reasoning alone does not establish a merchant action. If the evidence does not establish whether submission happened, use `unknown` with `submission_uncertain` instead of any `not_submitted` reason.

A successful payment tool call proves only that the tool returned a result. A `browser.pay` result with status `purchased` reports that the checkout workflow verified the merchant's confirmation; `pending_reconciliation` means the submission outcome is not yet established. Browser task status is supporting evidence, not proof of purchase success. Use `succeeded` only when the evidence verifies the merchant order.

Classify the latest established result for this purchase. A later verified order placement supersedes an earlier payment rejection. Conflicting evidence without a verified final result is `unknown`. Absence of success evidence is not proof of failure.

Users may edit this file to change when intermediate subagent progress should be surfaced back to the receiving parent agent.

Use this file only for `subagent_monitor.notify_main_agent` and `subagent_monitor.nothing_to_do`.

This monitor runs for a subagent subtree. Runtime handles terminal completion delivery deterministically before this monitor is asked anything.
This file specifies the exact allowlist for when intermediate updates may be surfaced to the receiving parent agent. Runtime chooses that parent: root/main for depth-1 coordinator events, or the coordinator for nested worker events.

## Hard Rule
- The default and expected action is `subagent_monitor.nothing_to_do`.
- You may call `subagent_monitor.notify_main_agent` only in the single case listed below.
- If the current state does not match that case exactly, you must call `subagent_monitor.nothing_to_do`.
- If there is any ambiguity, uncertainty, or incomplete information, you must call `subagent_monitor.nothing_to_do`.
- Do not make decisions on what is interesting / worthy of notification unless it fits the notification case below. Otherwise it will disrupt the recipient.

## The Only Notify Case
- All currently known child subagents of the coordinator are terminal and the coordinator itself is still non-terminal. This is the single allowed intermediate "all workers done, coordinator now synthesizing" update.

## Everything Else and Every Other Case is Noise
- Any single tool start or completed event is noise on its own, no matter the tool: inspection tools like `read` or `search` and mutating tools like `write`, `edit`, or `exec` all count.
- You must not notify for child spawns, partial child completion, or phase transitions before all children are terminal.
- You must not notify repeatedly once the "all children done, coordinator still running" state has already been surfaced.
- You must not notify for assistant chatter or for any terminal result, including the coordinator's own; runtime delivers terminal completions deterministically.

## Writing Style
- Runtime composes the delivered message from DB-backed event and state data.
- This file controls only whether to notify, not the wording of the delivered message.
