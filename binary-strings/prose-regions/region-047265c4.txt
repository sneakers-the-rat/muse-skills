Step 1: Identify the topic
Read the artifact's name and content description and identify what the artifact is about as a whole -- the subject, not one detail and not a metaphor. Some subjects share their name with an unrelated everyday thing; when that happens the topic is what the subject IS, not the word it shares. Then pick the icon that represents that subject directly.

Step 2: Find the tightest literal match
From the available icons, pick the one that most specifically represents the topic. Always prefer the tightest icon that still conveys the subject over a broader category icon. A golf artifact gets the golf icon, not a generic sports one. A forest-hiking artifact gets the forest icon if it exists, not a generic nature one. Step 3: Verify the pick
Before committing, run these four checks.
The guess test: if someone saw only this icon with no other context, could they reasonably guess the artifact's general topic? If the connection needs explaining, pick something more obvious.
The literal test: does the icon match what the artifact is ABOUT, or something loosely associated with it? A golf artifact gets a golf icon, not a basketball. A cybersecurity artifact gets a lock or a shield, not swiss cheese because of "holes".
The name test: did you pick this icon because its name matches the subject's NAME rather than what the subject is? An artifact about Apple the technology company does not get an apple depicting fruit; it gets a smartphone, laptop or chip icon. An artifact about Target the retailer does not get an archery target. Look up what the icon depicts, not what it is called.
The cleverness test: is the icon a pun, a visual metaphor, or a play on a word in the artifact's name or description? If yes, it is wrong. A band named Train does not get a train. Tracking a Taco Bell lettuce recall does not get a taco. A recall tracker for ball joints does not get a golf ball. A film tracker whose preview frame shows a turtle does not get a turtle. Match the topic, never the wordplay.
If the icon fails any check, go back to step 2 and take the next-best literal match.

## Never touch the old Space

The old Space folder `~/workspace/spaces/<slug>/` is the user's master copy
and backup. You only ever read it. Never write, edit, rename, move, or
delete anything under it, and never run its code: no actions, no builds, no
servers, no scripts. Parity is judged by reading source, never by executing
the old Space. This holds even after the migration succeeds. If the user
later wants the old Space deleted, that is a separate request they have to
make themselves.

Builders are bound by the same rule. Every instruction you send a builder
points only at your staged copies under `~/workspace/migration-<slug>/` and
says plainly that the builder must not read or write anything under
`~/workspace/spaces/`.

You prove the rule held, not just promise it, and the proofs are a script,
never something you retype. Before anything else, take the snapshot:

```
python3 /opt/hatch/skills/spaces/scripts/legacy_space_migration.py snapshot --slug <slug>
```

It records a checksum manifest of the old Space (leaving out files the
platform itself may touch), prints every database table with its row count
for the inventory, and writes the full data dump the builder will import
(`~/workspace/migration-<slug>/data.sql`). The same script's `verify`
command re-checks the manifest later: changed, deleted, and added files
all count. If it ever reports anything but MANIFEST CLEAN, the migration
failed: tell the user exactly what changed and stop.

All your scratch work lives in `~/workspace/migration-<slug>/`, never
inside the old Space.

## Step 1 — Inventory and stage (read-only)

Record in `~/workspace/migration-<slug>/inventory.md`:

- The `space.json` contents (name, slug, entry, verification).
- Every action in `actions/*.py`, and any background jobs under
  `actions/jobs/*.py`: each one's name, what input it takes, what it
  returns, what it validates or rejects, and what it changes. Mark any
  action whose effects leave the Space, such as sending mail or calling an
  outside service. This list is the parity contract for step 3. (An
  `AGENTS.md` in the old folder is the platform-seeded tombstone, not part
  of the Space.)
- Any entries under `~/workspace/cron.d/` this Space scheduled: the file's
  owner names the Space, or its command runs code under the Space root.
  Note what they did and when they ran, so the rebuild can declare the same
  scheduled behavior. Leave the old entries themselves alone.
- Every static asset the page uses: icons, background images, fonts.
  Copy each one into `~/workspace/migration-<slug>/assets/` and record its
  name and sha256.
- The frontend source under `src/`. The old frontend is already React;
  only the actions were Python. The rebuild keeps the same layout, flows,
  labels, and copy, and only changes how actions are called.

Generated folders such as `.space-build`, `node_modules`, or `.venv` are
clues at most: never port their contents as the new implementation.

The `snapshot` command already printed every table and its row count, and
wrote `data.sql` when there was data: record the counts in the inventory.
If it printed "no data", write that in the inventory and skip step 4. When
you read old files yourself, read only; the script opens the database
read-only, and so do you.

## Step 3 — Check the actions

Reading the new artifact's files to verify this migration is part of this
playbook: it is not the malfunction-inspection flow, and you change nothing
while doing it.

For each action in the inventory, check the new source against the parity
contract: same name, same inputs, same outputs, same validation and failure
behavior. Someone calling the old action and the new one must not be able
to tell them apart. Tick each action off in `inventory.md` when the source
matches the contract and the builder's test run exercised it. An action
marked as having outside effects is ticked on source match alone and stays
annotated as untested: never fire it during the migration, and name it to
the user in the handoff.

Never add, merge, or "improve" actions or contracts. If an old action has a
bug the user never asked about, replicate the behavior and mention the bug
to the user separately.

## Step 4 — Verify the data

Skip this step if the snapshot printed "no data". Otherwise, after the
build succeeds and while no build is running, run:

```
python3 /opt/hatch/skills/spaces/scripts/legacy_space_migration.py verify --old-slug <old-slug> --new-slug <new-slug>
```

It re-checks the manifest and compares every table of the old and new
databases read-only, in both directions: row counts and full content
digests, so a missing or extra table fails too.

ALL MATCH, and exit code 0. On any mismatch, stop and tell the user what
differs. The fix goes back through the builder as an `edit`; never repair
the new database by hand, and never touch the old one at all.

## Step 5 — Verify the look and the assets

The new page must look and feel like the old one: same layout, same flows,
same labels and copy, judged against the old frontend source. For every
asset in the inventory, verify the copy the builder placed under the new
artifact's client assets has the same sha256 you recorded in step 1.
Nothing gets redesigned, restyled, or modernized.

## Step 6 — Final checks

- The build succeeded and the published page renders.
- Every action in the parity checklist is ticked, with any untested
  outside-effect actions named.
- The data verification in step 4 reported ALL MATCH, and the migrated
  data shows up in the page the way it did in the old Space.
- Any scheduled behavior from the step 1 inventory is declared on the new
  artifact: its `refresh_triggers` match the cron entries you recorded,
  and no new cron entries were written.
- Run the `verify` command one last time as the final gate: it must end
  with MANIFEST CLEAN, ALL MATCH, and exit code 0, proving the data still
  matches and the old Space is byte-untouched.
